## Architecture proved

The Avalonia shell uses only standard .NET process/stream APIs for the first headless-core bridge:

- child executable SHA-256 verified before launch;
- child process launched with `UseShellExecute=false`;
- stdin/stdout/stderr redirected as inherited anonymous pipes;
- no localhost TCP/HTTP/gRPC server;
- ECO-compatible framing: 4-byte big-endian payload length followed by JSON;
- maximum request/response frame: 8 MiB;
- protocol version = 1;
- every response must match the request ID;
- requests serialised through one client gate so frame streams cannot interleave;
- stderr drained without mirroring diagnostic text into the synthetic user interface;
- normal shutdown closes stdin and waits for child exit;
- non-cooperative child shutdown kills the complete process tree and requires `WaitForExit` confirmation.

No JSON-RPC, gRPC, named-pipe or third-party .NET IPC package was needed for this proof.

## Defect found and corrected during qualification

An earlier run exposed a useful lifecycle defect in the first adapter implementation: an optional PID receipt was passed as a relative path. Because the child/shell package has its own working directory, receipt creation failed after the child process had already started. The first implementation could therefore throw after `Process.Start()` without first proving the child was terminated.

The qualification lane corrected both issues before the final PASS:

1. qualification receipt paths are canonicalised to absolute paths;
2. if any setup action after `Process.Start()` fails, `CoreProcessClient.Start` now kills the full child tree, waits for termination and disposes the process before rethrowing.

The failing runs are preserved in GitHub Actions history rather than removed from the audit trail.

## Product-admission hardening still required

- if cancellation/interruption occurs after a frame begins, treat the channel as terminal and restart the child rather than attempting to continue on a potentially desynchronised stream;
- bind expected core SHA-256 to the controlled package manifest/SBOM rather than environment variables;
- decide whether the threat model requires an additional startup nonce/authenticated handshake beyond exact executable identity plus privately inherited pipe handles;
- use the current sandbox/job/worker process controls where applicable rather than weakening existing ECO containment;
- prove the full current Go core + Avalonia shell on the real controlled source derivative before replacing the existing Windows presentation layer.

## Decision

**Avalonia ↔ existing Go headless core over privately inherited framed stdio is the selected first integration architecture.**

Named pipes (`microsoft/go-winio`, MIT) remain a future option only if ECO later needs independently reconnectable or multi-client local IPC. They are not justified for the first single-shell/one-core architecture.
